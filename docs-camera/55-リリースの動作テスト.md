# リリースの動作テスト（Windows 11 で Electron ポータブルを実機検証）

GitHub Releases に上げた **Windows 用 Electron ポータブル exe** を、配布先のユーザーと
同じ手順で実機（Windows 11）にダウンロードして起動し、**`?tx` / `?rx&obs` の HTTP 応答・
バージョン一致・WS 中継の疎通**まで自動で確かめるスクリプト。配布前のスモークテスト用。

アプリのビルドは [58-WindowsアプリにするElectron.md](58-WindowsアプリにするElectron.md)、
通常運用（ソースから）は [14-Windowsで動かす.md](14-Windowsで動かす.md)、テスト全体の方針は
[54-テスト.md](54-テスト.md) を参照。ここは「公開済みリリースを落として動くか」だけを見る。

> 旧 zip 配布（`guruguru-relay.exe` + `start.bat`、win-v1.9.x 以前）向けの旧版テストは
> このファイルの git 履歴を参照。本スクリプトは Electron 配布物専用。

## 何をするスクリプトか

`windows\test-release-win11.ps1` が次を順に実行する（ユーザー手順そのまま）:

1. GitHub の **最新リリース**（`releases/latest`）から `*-portable.exe` アセットの URL を取得
2. **ダウンロードフォルダ**へ exe を保存（`curl.exe -L` でリダイレクト追従）し、
   `Unblock-File` で Mark-of-the-Web を除去
3. **ポータブル exe を起動**（`%TEMP%\guruguru-avatar-portable` へ自己展開 → 子プロセス
   `Guruguru Avatar` が内蔵サーバ `127.0.0.1:5179` で待ち受ける）
4. **curl で検証**:
   - 送信側 `http://127.0.0.1:5179/index.html?tx`
   - OBS 受信側 `http://127.0.0.1:5179/index.html?rx&obs`

   どちらも **HTTP 200 / HTML 本文 / `<title` を含む**なら合格。
5. **`GET /version.json` で配布物の同一性を検証**: ビルド時に焼き込んだ
   `{version, sha, date}` を取得し、リリースタグ（`win-vX.Y.Z`）の X.Y.Z と一致するか確認
6. **WS 中継 `/__relay` の実疎通を検証**: `role=rx` と `role=tx` の 2 本の WebSocket を張り、
   tx から送った 1 フレームが rx に届くことを確認（HTTP 200 だけでは中継の生死は分からない）
7. 後片付けでアプリを停止（`-KeepRunning` を付けると起動したまま残す）

## 使い方

Windows 11 上で `guruguru-avatar\windows\` を開いて:

### かんたん（ダブルクリック）

`test-release-win11.bat` をダブルクリックするだけ。中で PowerShell を
`-ExecutionPolicy Bypass` で呼ぶので、実行ポリシーを触らなくてよい。

### PowerShell から

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File windows\test-release-win11.ps1
```

オプション:

| オプション | 既定 | 説明 |
| --- | --- | --- |
| `-Repo <owner/repo>` | `tommie-jp/guruguru-avatar` | 対象リポジトリ |
| `-Tag <win-vX.Y.Z>` | 最新リリース | 特定タグを検証する |
| `-LocalExe <path>` | なし | 開発モード: DL せずローカルの portable exe を検証 |
| `-TimeoutSec <秒>` | `120` | サーバ起動を待つ最大秒数（初回は展開+検疫で延びる） |
| `-KeepRunning` | off | 検証後もアプリを止めず残す（画面確認したいとき） |
| `-SkipDownload` | off | ダウンロード済み exe をサイズ一致時のみ再利用する |

```powershell
# 起動したまま残して、ブラウザ/OBS で目視確認したい
powershell -NoProfile -ExecutionPolicy Bypass -File windows\test-release-win11.ps1 -KeepRunning

# リリース前に WSL のビルド成果物を直接検証（開発モード）
powershell -NoProfile -ExecutionPolicy Bypass -File windows\test-release-win11.ps1 `
  -LocalExe '\\wsl.localhost\Ubuntu24.04\home\tommie\39-guruguru-avator\guruguru-avatar\dist-electron\GuruguruAvatar-1.10.0-portable.exe'
```

## 出力と終了コード

最後に検証結果を表で出し、総合判定を返す。

```text
==================== 検証結果 ====================
Label                           Code Pass
-----                           ---- ----
tx (送信側)                        200  True
rx (OBS 受信側)                    200  True
version.json (1.10.0 == 1.10.0)      True
WS 中継 (tx→rx)                        True

[OK]    総合判定: PASS ✅  (tx / rx / version / WS 中継)
```

- **終了コード 0** … 全項目 PASS
- **終了コード 1** … いずれか失敗、またはサーバが時間内に起動しなかった（FAIL）
- **終了コード 2** … 事前条件を満たさず**検証せずに中断**（アプリが既に起動中／
  ポート 5179 が他プロセスに使用中）。FAIL とは区別される

CI や別スクリプトから呼ぶときはこの終了コードで合否を判定できる。

## 仕組みの要点（Electron 固有の設計）

- **偽 PASS を 2 経路で防ぐ**:
  1. アプリは単一インスタンス制御があるため、既存の `Guruguru Avatar` が居ると新規起動が
     「既存窓のフォーカス」に化けて**旧バイナリを検証してしまう**。→ 事前チェックで
     既存プロセスが居たら exit 2 で中断する。
  2. 内蔵サーバは 5179 使用中だと ephemeral ポートへ逃げるため、5179 に居る**別人のサーバ**へ
     curl して合格する事故があり得る。→ 事前に 5179 の空きを必須にし、起動後は
     「5179 の所有 PID が今起動したランチャーの**子孫**であること」を親 PID チェーンで検証する。
- **停止は必ず「子 → ランチャー」の順**: ポータブルはランチャー（DL した exe）が
  `%TEMP%` へ展開して子 `Guruguru Avatar` を待つ二重構造。ランチャーを先に殺すと子が
  オーファン化してポートを握り続け、次回テストの偽 PASS 源になる。子を先に止めると
  ランチャーが展開物を自己掃除して約 1 秒で終了する。強制終了が必要な場合のみ
  `taskkill /T /F` に落ち、`%TEMP%\guruguru-avatar-portable`（`portable.unpackDirName` で
  固定）を明示削除する。
- **curl は実体を使う**: `C:\Windows\System32\curl.exe` を直接呼ぶ。PowerShell の
  `curl` エイリアス（`Invoke-WebRequest`）ではない。
- **SmartScreen で止まらないように**: ダウンロードした exe から `Unblock-File` で
  Mark-of-the-Web を外す。なお curl 経由の DL は MotW が付かないため、**実ブラウザで
  DL したときの SmartScreen 体験は自動テストでは再現されない**（リリース時に一度は
  手動確認する。[58-WindowsアプリにするElectron.md](58-WindowsアプリにするElectron.md) の注意参照）。
- **WS 疎通は .NET の ClientWebSocket** で行う（`System.Net.WebSockets`）。
  `/__relay?role=rx` → `/__relay?role=tx` の順に接続し、tx から送った
  `{"type":"e2e-ping"}` が rx に届けば合格（peer 通知などの他フレームは読み飛ばす）。

## 注意

- **テスト中にアプリの窓が一瞬開く**（実ユーザー体験どおり・無害）。`-KeepRunning` を
  付けない限り最後に自動で閉じる。
- **デプロイ機＝常用機の場合**: アプリを使用中（配信中）は事前チェックで exit 2 になり
  実行できない。アプリを終了してから回すこと。
- **API レート制限**: 未認証だと GitHub API は 60 回/時。引っかかるなら環境変数
  `GITHUB_TOKEN` を入れておくと `Authorization` ヘッダを付けて緩和する。
- **ダウンロードフォルダ**はレジストリの既知フォルダ（Downloads の GUID）から解決し、
  取れなければ `%USERPROFILE%\Downloads` にフォールバックする。

## WSL2 (Ubuntu 24) から実行する

WSL2 は interop で Windows の `.exe` を実行できるので、**WSL のシェルから `powershell.exe`
経由で同じテストを丸ごと回せる**（実証済み）。

```bash
WINPS1="$(wslpath -w "$PWD/windows/test-release-win11.ps1")"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$WINPS1" -Tag win-v1.10.0
# -Tag を省くと最新リリース(releases/latest)を対象にする
```

ポイントは **アプリも curl.exe も Windows プロセスとして動く**こと。両者は Windows の
ループバック（`127.0.0.1`）で会話するので、WSL のネットワークが NAT モード
（`wslinfo --networking-mode` が `nat`）でも境界をまたがず通る。

- **WSL の Linux `curl` で `http://127.0.0.1:5179` を叩かない**こと。NAT モードでは WSL の
  ループバックと Windows のループバックは別物なので届かない（mirrored モードなら可）。
  本スクリプトは中で Windows の `curl.exe` を呼ぶのでこの問題を回避している。
- `-LocalExe` に WSL ファイルシステム上のビルド成果物（`\\wsl.localhost\...`）を直接
  指定して起動できることは実機確認済み（ポータブルは NSIS 自己展開形式のため、
  旧 Bun バイナリと違い 9p 越しでも起動できる）。

## doDeploy.sh win との統合

`./doDeploy.sh win`（および `./doDeploy.sh all` の後半）は、リリースをアップロードした後に
**GitHub 上でアセットが取得可能になるまで待ってから、このテストを自動実行する**:

1. `gh release upload`（または `create`）で `win-v<version>` を配置
2. API でアセットが `state=uploaded` かつローカルと同サイズになり、実ダウンロード
   （先頭 1 バイトの range GET）が 200/206 を返すまでポーリング（最大 ~3 分）
3. `powershell.exe -File windows\test-release-win11.ps1 -Tag win-v<version>` を実行
4. テストが FAIL（exit≠0）なら `doDeploy.sh` も失敗終了する

スキップしたいとき:

- `DEPLOY_SKIP_WIN_TEST=1 ./doDeploy.sh win` … テストだけ飛ばしてリリースまでで止める
- `powershell.exe` が無い環境（素の Linux CI 等）では自動でスキップし、手動実行コマンドを案内する
